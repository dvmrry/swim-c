## Orientation (read this first)

**What swim is now:** a personal, single-binary, vi-mode macOS browser. C core +
Objective-C AppKit/WebKit UI + one Swift module. Not an agent platform — the
HTTP API and MCP sidecar were deleted (see `docs/ROADMAP.md` Direction). Decision
context lives in the project memory file `direction-daily-driver.md`.

**Build / test / run:**
- `make` → builds `./swim` (single binary; no more `swim-mcp`).
- `make test` → `test/storage_test` + `test/zoom_test`, built as standalone
  binaries, never linked into release. **This is the regression gate — keep it green.**
- `make clean && make` warning baseline is **10** (1 `-Woverlength-strings` in a
  generated `.inc`, 9 GNU `?:` in `ui.m`). Introduce no new categories.
- Run: `./swim [urls...]`, `--app <url>` (chromeless), `--profile <name>`.

**Mixed-language build (precedent: `Zoom.swift`):** Swift modules export the C ABI
via `@_cdecl`, so C/ObjC callers link unchanged. `SwiftBridge.h` is the
`-import-objc-header` bridge exposing C funcs *to* Swift. The Makefile compiles
per-file `.o` (clang for `.c`/`.m`, swiftc for `.swift` with
`-parse-as-library -module-cache-path /tmp/swim-swift-module-cache`) and links
with the `swiftc` driver so the runtime resolves. Gotcha: without the
module-cache-path override, swiftc tries to write under `~/.cache` and fails in a
sandbox.

**⚠ Verification is GUI-only now.** Removing the API removed the ability to drive
swim programmatically. To verify UI behavior you need computer-use + Screen
Recording (macOS), or ask the user to spot-check. Pure-C logic (storage, zoom,
parsers) is still verifiable headlessly via `make test`-style harnesses — prefer
that. Don't claim a UI feature works without runtime observation.

**Delegation pattern that worked this session:** Opus does boundary/judgment work
and review; Codex (`codex:codex-rescue` subagent → `codex-companion.mjs task`)
does mechanical implementation from a precise self-contained spec, then Opus
independently builds/tests and reads the risky part of the diff before committing.
Use it to save cost on well-specified work.

**Conventions:** no `Co-Authored-By` in commits. `docs/plans/` is gitignored
(local working docs). `git push` and `git branch -d` are blocked by the session
permission classifier — the user runs those.

## The work, ranked

### 1. `storage.c` → Swift + frecency completion  ★ marquee

**Why:** `storage.c` still holds the hand-rolled JSON parser (patched twice this
session — `ftell` guard, object-bounded field parsing). It stores history/session,
so a parse bug loses real user data. Codable deletes the parser and the whole
bug class there. And it's where **frecency** — the single biggest daily-feel
upgrade — naturally lives. One move, two payoffs.

**Gotcha that makes this harder than `zoom.c` was:** `zoom.c` had a clean 3-function
opaque API. `storage` exposes its structs — `main.m`'s `on_command_complete` reads
`app.bookmarks.entries[i].url` directly, and the bookmarks-list command iterates
entries too. A Swift owner can't hand C a struct array to index. **So the port is
"port + refactor callers onto a proper ABI," not a drop-in.** That refactor is one
frecency wants anyway.

**How:**
1. Redefine `storage.h` as a *function-only* ABI — no exposed struct internals.
   Add: `int storage_search_ranked(Storage*, const char* query, char urls[][2048],
   char titles[][256], int max)` returning ranked results into caller buffers;
   plus `storage_count()` / `storage_get(i, url_out, title_out)` if the
   bookmarks-list command still needs iteration. Refactor the 2–3 caller sites in
   `main.m` to use these (they stop touching struct memory).
2. Implement `Storage.swift`: `struct Entry: Codable { url; title; time; visitCount }`,
   persisted via `JSONEncoder`/`Decoder`. Export the ABI via `@_cdecl`. Migration:
   existing `history.json`/`bookmarks.json` have no `visitCount` — make it default
   to 1 (Codable default). Keep reading the current on-disk format.
3. **Frecency (phase 1 — ranking, high value / low UI risk):** `storage_add`
   already dedups+updates existing entries — extend it to bump `visitCount` and
   `lastVisit`. Score = `visitCount × recencyMultiplier(now − lastVisit)`, buckets
   ≈ Firefox: `<1h ×4, <1d ×3, <1wk ×2, <1mo ×1, else ×0.5`. `storage_search_ranked`
   sorts by score desc (bookmarks can get a flat bonus — intentional saves).
   Result: Tab lands the *right* URL first. This alone is the win.
4. **Frecency (phase 2 — visible candidates, more UI work):** render up to N ranked
   candidates under the command bar in `ui.m` (AppKit, stays ObjC). Keyboard-only,
   qutebrowser-minimal. Separable from phase 1 — do it after.

**Done when:** `make test` green (extend `test/storage_test.c` to cover ranking +
the visitCount round-trip + old-format migration); the hand-rolled parser
(`json_string_end`, `json_escape`/`unescape`) is deleted; typing a fragment and
hitting Tab lands the most-frecent match first; existing history/bookmarks load
unchanged.

### 2. Session autosave  ★ small, high daily value

**Why:** `session.json` is written only on clean quit (`main.m` after `[NSApp run]`)
and `:session save`. A crash or force-kill loses your open tabs — worst-feeling
failure for a daily driver. History already saves per-navigation, so only tabs are
at risk.

**How:** add a tiny `autosave_session()` (wraps `collect_tab_urls` +
`session_save(app.session_path, …)`, both already exist) and call it after tab
open, tab close, and navigation-commit. The write is ≤128 URLs — cheap, no
debounce needed. Skip in `--app` mode (matches existing guard).

**Done when:** open several tabs, `kill -9` swim, relaunch → tabs restored. Pure C,
no port risk — good warm-up task.

### 3. History eviction (do after frecency)

**Why:** `MAX_ENTRIES` is 4096; `storage_load` currently just stops at the cap.
Once entries carry `visitCount`/`lastVisit`, evict lowest-frecency instead of
truncating arbitrarily.

**How:** on insert-at-cap, drop the min-score entry. Revisit whether 4096 is still
the right number once real frecency data exists.

### 4. Memory consolidation (cheap; orients future sessions)

**Why:** `MEMORY.md` still has `## API Server & MCP` and `## Network Inspection
Notes` sections describing **deleted** code, calls it a "three-binary design" (now
one), and lists fixed items (per-domain zoom, address-bar completion) under "Known
Gaps." A future session reads stale facts.

**How:** run the `consolidate-memory` skill; prune/rewrite those sections against
current `ROADMAP.md` + `README.md`. `direction-daily-driver.md` is current and
correct — use it as the source of truth for the direction.

### 5. À la carte Swift ports (optional, low priority)

`config.c` / `theme.c` / `userscript.c` are small line-parsers Foundation would
simplify — but they're stable and low-pain, so only port if you're already in
Swift-mode nearby. See the Do-Not list re: `ui.m`/`main.m`.

## Do NOT do (anti-backlog — protects future effort)

- **Don't port `ui.m`/`main.m` to Swift.** ~2,900 lines of AppKit/WebKit glue that
  translates ~1:1, deletes almost nothing, and risks bugs in working UI code. Only
  touch it if overhauling the UI for its *own* reasons (e.g., adopting async/await
  WebKit APIs) — not for language purity. A "full Swift" rewrite is explicitly not
  worth it; the excision already removed its main justification.
- **Don't resurrect the automation layer** (HTTP API / MCP / event stream /
  recording / `:ai`). Decided and deleted; that space is better served elsewhere.
- **Don't hand-harden the remaining C** beyond what's done — it's small, stable,
  and now test-covered.
- **Don't chase a big-bang rewrite branch.** Strangler only: one working binary at
  all times, `make test` as the parity gate, each step committed and revertible.
